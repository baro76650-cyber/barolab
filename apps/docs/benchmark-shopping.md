# 말로 장보기 — 경쟁 근거와 UX 재설계 제안

조사일: 2026-10-14 KST. 소스 수정·배포 없이 작성한 비교·제안이다. 결론은 ‘기능을 더 많이’가 아니라 **매장에서 빨리 체크하고, 틀린 입력을 쉽게 고치고, 다음 장보기에 필요한 것만 다시 쓰는 흐름**을 먼저 검증하자는 것이다.

## 근거 범위와 신뢰도

공식 Google Play 상세 3개, 개발사 FAQ 1개, 상세페이지에 노출된 리뷰 각 3개(총 n=9), 공식 홍보 이미지 각 1장(총 3장)을 확인했다. 이미지 파일은 외부 TEMP에만 내려받아 직접 보았으며 프로젝트/앱 자산으로 복제하지 않았다. 경쟁 앱을 설치·실행하거나 해당 APK를 REA로 분석하지 않았다. 아래 화면 흐름은 홍보 이미지·개발사 설명으로 재구성한 것이며 실제 모든 탭·오류·가입·결제 동작을 검증한 사용기와 다르다.

‘최근 리뷰’ 정렬로 전체를 수집한 표본이 아니다. 공개 상세에 선택 노출된 영어 리뷰이며 작성자의 국적·나이·기기·한국어 사용성은 알 수 없다. Listonic/OurGroceries 페이지 하단은 미국·영어, Bring은 스페인·영어였다. 미국을 지정한 URL은 도구에서 열리지 않아 실제 열리는 기본 URL을 사용했다. 평점·리뷰 수는 지역·기기 섹션에 따라 달라지고 설치 범위는 누적 다운로드의 구간일 뿐 월간 활성·매출·좋은 UX의 인과 근거가 아니다.

## 현재 말로 장보기와의 격차

현재 `shopping/src/main/java/com/barolab/voicebasket/MainActivity.java`, `BasketStore.java`, `BasketParser.java`, `VoiceInput.java`를 기준으로 읽기 대조했다. 다중 목록·직접 수량 편집·체크·한 단계 복원·완료 보관·템플릿 복사·텍스트 공유·18/22/28sp는 이미 있다. 음성은 수정 가능한 원문→미리보기→사용자 확정이 있고 수량·유사 상품을 추측하지 않는다. 실기기 한국어 인식 성공은 별도 검증 대기이며 에뮬레이터 키보드 성공으로 대신하지 않는다.

| 현재 코드에서 관측한 상태 | UX 가설·격차(아직 사용자 검증 아님) |
|---|---|
| 항목마다 흰 패널+큰 체크 행+‘수량·이름 수정’ 버튼. 체크 후 전체 render 재구성 | 긴 목록에서는 같은 화면에 보이는 항목이 적고 위치/초점이 흔들릴 수 있다. 정확한 흔들림·실패율은 실제 화면/접근성 테스트 필요 |
| 추가는 상세와 다른 composer 화면이며 원문·음성 조작·옵션·미리보기·추가가 세로로 쌓임 | 키보드와 큰 글씨에서 ‘지금 무엇을 확인하고 어디를 눌러야 하는지’ 부담. 안전한 확인 단계를 없애기보다 같은 작업 영역에 정리할 필요 |
| 템플릿/보관 재사용은 목록 전체 복사, 기존 항목을 선택해 일부만 담는 마스터/검색 흐름 없음 | 주간 장보기에서 필요한 4개만 다시 쓰려면 복사 후 여러 항목을 지워야 할 수 있음 |

이는 경쟁사보다 무조건 나쁘다는 판정이 아니다. 소유 코드의 구조와 비교해 시험할 과업을 정한 것이다. 계정 없는 로컬 사용·매장 조작 중 광고 없음·틀린 인식의 확정 방지는 계속 보존할 강점이다.

## 제안하는 핵심 3가지와 수락 기준

아래는 구현 완료나 실측 결과가 아닌 다음 프로토타입의 목표다. 먼저 기존 UI와 같은 가상 목록으로 비교한다.

### 1. 매장에서 체크하기 쉬운 목록

제안: ‘남은 것’ 중심의 텍스트 행, 구입한 항목은 명확한 별도 구역, 체크 수/남은 수를 작게 고정 표시. 이름·수량은 한 덩어리로 읽고 편집은 행의 보조 조작으로 연다. 모든 항목에 편집 버튼을 크게 반복하지 않는다. 자동 재정렬이 방금 보던 위치를 밀지 않도록 하며 복원은 바로 찾을 수 있게 한다. 그림/AI 추천/광고 상품을 목록 본문에 섞지 않는다.

검증 기준:

- 20개 가상 항목에서 지정 5개 체크·1개 오체크 복원을 수행하고 남은 수·데이터가 예상과 정확히 일치한다.
- 체크·복원 직후 같은 주변 항목을 계속 찾을 수 있고 불필요한 화면 재생성/초점 손실이 없어야 한다. TalkBack 사용자도 체크 상태와 항목명을 함께 들을 수 있어야 한다.
- 주요 터치 영역 최소 48dp, 앱28sp+시스템1.3배·가로에서도 이름/수량/복원 버튼이 가려지지 않는다. 무조건 고정 행 높이를 강제해 긴 상품명을 자르지 않는다.

### 2. 한곳에서 고치고 확인하는 입력

제안: 한 추가 작업 영역 안에서 키보드·음성 선택→인식된 원문 수정→분리된 항목 확인→명시적 추가가 이어지게 한다. 음성 상태·취소·원문과 확정 전 상태를 짧게 표시하고 고급 분리 옵션은 필요할 때만 연다. 키보드가 떠 있어도 다음 행동과 오류가 가까이 보이게 한다. 안전한 추가 전 미리보기는 유지한다.

검증 기준:

- ‘우유, 달걀, 두부’와 일부러 틀린 낱말을 넣은 입력을 고쳐서 3개로 확정한다. 미리보기 수정 전 내용이나 수량이 자동으로 저장되지 않아야 한다.
- 원문을 고친 뒤 낡은 미리보기로 추가할 수 없고, 새 결과를 확인한 뒤 한 번만 커밋한다. 권한 거부·서비스 없음에도 키보드 완주가 가능하다.
- 회전·홈 이동·취소 때 마이크가 해제되고 기존 확정 목록은 불변이다. 인식 오류를 모델이 ‘알아서’ 다른 상품으로 바꾸지 않는다. 한국어 실제 성공은 동의한 실제 기기에서 별도로 기록한다.

### 3. 다음 장보기에 필요한 것만 재사용

제안: 최근/템플릿/보관 목록에서 항목을 선택해 새 목록에 담는 로컬 흐름. ‘전체 다시 사용’도 남겨 두되 사용자가 10개 중 필요한 4개만 고르기 쉽게 한다. 이름으로 찾기는 로컬 데이터만 사용하고, 분류/추천을 추가하더라도 사용자 명칭을 보존한다. 유사 상품 자동 병합 없이 정확 중복 처리 결과를 보여 준다.

검증 기준:

- 10개 원본에서 4개 선택→새 목록에는 해당 4개만, 원본 10개는 체크/이름/수량까지 불변이다. 새 목록 체크는 초기화되고 수량은 확인한 값대로 유지된다.
- 재시작·회전 후 저장된 선택 결과가 정확하며 이중 클릭으로 복제 목록이 생기지 않는다. 정확 중복 옵션의 유지/건너뛰기 수를 확인할 수 있다.
- 목표 연령 참여자가 도움 없이 ‘복사한 새 목록’과 ‘원본 템플릿’을 구별하는지 시험한다. 혼동하면 기능 확대 전에 문구·흐름을 수정한다.

## 과잉 기능을 막는 우선순위

위 3개 과업을 우선한다. 실시간 가족 동기화·계정·클라우드 백업, 가격 합계/단위 가격, 바코드·제품 사진·생성 AI·조리법·쿠폰·결제·워치 연동은 별도 후보 묶음으로 둔다. 경쟁사에 있다는 이유만으로 추가하지 않는다. 특히 우리 타깃의 ‘함께 장보기’ 수요가 실제로 확인된 뒤 동기화의 서버 비용·충돌·접근 권한·삭제/보안·오프라인 정책을 비교한다. 이 목록은 실행 승인 요청이나 지금 구현하겠다는 약속이 아니다.

## 공동 개발 프로세스 제안

1. **경쟁 근거:** 공식 상세/개발사 문서/노출 리뷰/화면의 날짜·지역·표본을 기록한다. 실행 사실과 광고 설명을 분리한다.
2. **과업 흐름:** 사용자 문제 하나마다 시작·완료·실수·취소·재방문을 그린다. 기능 목록이 아니라 성공해야 하는 동작을 먼저 정한다.
3. **디자인 프로토타입:** 독립 색·구성으로 클릭 가능한 핵심 3화면과 큰 글씨·빈/오류·권한 거부 상태를 만든다. 코드 이전에 비교할 수 있어야 한다.
4. **사용성:** 예를 들어 동의한 5명 중 목표 연령 3명 이상으로 작은 탐색 테스트를 제안한다. 아직 모집·시험하지 않았다. 기존/새 흐름의 제시 순서를 섞고 같은 가상 목록으로 완주·오조작·도움 요청·단계/시간을 관찰해 표본 수와 함께 기록한다. 경쟁사 사용성 수치를 만들어 비교하지 않는다.
5. **코드:** 통과한 과업을 clean implementation으로 구현한다. 수명주기·저장 원자성·취소·권한·광고 제외 상태를 검증한다. REA는 소유/허용된 APK의 manifest·구조 확인 보조로 쓰며 UI 모양만으로 실기기 동작을 인정하지 않는다. 경쟁 앱의 코드·자산 추출/재사용을 전제로 하지 않는다.
6. **출시:** 독립 QA·실제 화면·최종 artifact hash·앱 이름·개인정보·데이터 보안·트랙 상태를 대조하고 내부→비공개→정식 절차를 구분한다. 테스트 ID와 수익 실측을 섞지 않는다.

## 실제 API 초안과 수동 검토 기록

인증된 로컬 FreeLLMAPI `auto` 실제 호출: 반환 모델 `liquid/lfm-2.5-2.6b:free`, status `ok`, 4,570ms, prompt420+completion889=총1,309토큰. 후보는 ‘매장 체크’를 매장 위치/영업시간 검증으로 오해했고, 즉시 자동 저장·체크마다 확인 창·템플릿 3개 제한을 제안했다. 이 내용은 근거와 현재 과업에 맞지 않아 폐기했다. 위 3가지와 수락 기준은 관측 근거를 대조해 수동 작성했으며 모델 코드를 실행하거나 후보를 자동 반영하지 않았다.
